## H1. A See-only member can give every member Edit on everything (the old-format path)

> **Fixed** (follow-up, after the share code moved to
> `public/js/shared/share-core.js`). The old-format path now runs only when
> this computer's own lock for the project holds a bare key and the project
> has never been seen in the team's shape (a `v3` mark kept in `share_kv`
> from the first v3 document, sharing or re-key on). An old-shape document in
> any other project is refused (counted in `refused`), and the owner's or an
> admin's computer writes a proper one over it. `migrate()` takes the old
> switches only when the owner's signature on them checks against the
> pinned owner key; otherwise every kind gets its default. Test: "a See-only
> member cannot pass off a document in the old shape…" in
> `test/share.test.js`.

**Where:** `lib/share.js:525-529` (syncOne), `lib/share.js:589-603`
(migrate), `lib/share.js:395-409` (mergeLegacy); the service accepts the
document from any joined member, `sync-worker/src/shares.js:160-169`.

**What goes wrong:** every member's lock holds the project key `k`, which
seals the outer document. When the owner's (or an admin's) Switchboard
opens a document whose `v` is not 3, it treats it as a project shared
before the team. It then:
1. merges its `pages` and `items` with **no signature check**
   (`mergeLegacy`), and
2. runs `migrate()`, which reads the levels from `outer.meta.policy.shares`,
   a field the document's writer controls. Any truthy value becomes
   `'edit'` for **every** member. The owner's computer then signs that
   policy and re-keys, which hands every member the keys to every kind.

So a member with See (or None) on pages, to-dos, Activity or About can
write `{ v: 2, meta: { policy: { shares: { pages: true, tasks: true,
repos: true, activity: true, about: true } } }, pages: [...], items: [...] }`,
seal it with `k` and PUT it (the service only checks that they joined). On
its next round the owner's computer gives everyone Edit on everything,
shows everyone's activity to everyone, and takes their unsigned edits.
Those edits also land anywhere on the owner's computer (see H3), since
`mergeLegacy` looks rows up by uid alone.

**How to reproduce:** in `test/share.test.js` terms: owner shares with a
member at `{ pages: 'see', activity: 'none' }`. As the member, fetch the
doc, `seal({ v: 2, meta: { policy: { shares: { pages: true, activity: true } } }, pages: [{ uid, title: 'x', body: 'changed', updated_at: Date.now() + 1 }] }, k)`,
PUT it with the current version and epoch, then run `syncShares()` as the owner.
`policyOf(id).grants[member].kinds.pages` is now `'edit'`, and the page
body is `'changed'`.

**Suggested fix:** only take the old-format path when this computer's own
record says the share is old (a `share_kv` flag set when the share was
first read under the old format), never because of what a document says.
Once any v3 document or signed policy has been seen for a share, refuse
anything that isn't v3 (count it in `refused`). In `migrate()`, never read
levels from the document. Use this computer's own copy of the old
switches, or the safe defaults (`DEFAULT_KINDS`, Activity none). Better
still, remove the old-format path once no old shares are left: the team
model shipped today, so there may be none in use.

## H2. An invitation by email can be taken by anyone who makes an account with that address

> **Fixed in part** (follow-up). Joining now needs the link's secret, or the
> owner's say-so. `POST /v1/share-invites/<pid>/accept` (Join on Now, without
> the link) marks the invitation `asked` instead of `accepted`. The owner's
> computer no longer hands keys over for it on its own: Settings, Team shows
> the address with **Let in** (`admitInvite`, `/api/share/admit`), and the
> joiner sees "You asked to join…". Following the link still joins in one
> step, and it also turns an `asked` invitation into a join. An owner
> computer on an older version ignores `asked`, so it fails safe. Test: "an
> invitation taken without its link waits for the owner to let them in" in
> `test/share.test.js`.
>
> **Still open, needs a decision:** the service still does not check that an
> account owns its address, either at password sign-up or for Microsoft's
> unverified email. So (a) someone who signs up first with the invited
> address blocks the real person, and shows on the owner's Team page as
> asking to join, and (b) inviting an address that already has an account
> seals the keys to that account straight away. Closing this needs the
> service to send a code by email at sign-up (a mail sender, possibly paid,
> which is the owner's call). The Microsoft fallback should then use the
> `…@users.switchboard` placeholder when the email is unverified.

**Where:** `sync-worker/src/index.js:200-208` (password sign-up never
checks the email), `sync-worker/src/index.js:74-75, 93-102` (a Microsoft
sign-in creates an account with an email Microsoft does not vouch for),
`sync-worker/src/shares.js:77-81, 96-107` (lists and accepts waiting
invitations by email hash, without the link's secret), and `lib/share.js:693-699`
(the owner's computer then hands over the keys).

**What goes wrong:** the invitation's design says the link's secret is
what lets someone join ("The secret rides after the #…"). But
`GET /v1/share-invites` lists every waiting invitation for the signed-in
account's email, and `POST /v1/share-invites/<pid>/accept` accepts one
with no token. The service's accounts are not proof of owning an address:
`/v1/signup` takes any email with a password, and the Microsoft provider
creates an account under whatever `email` the ID token carries
(`verified: false`, but `fallback = email` is still used at line 97). So
the owner invites `jordan@acme.com`, who has no account yet. Anyone who
signs up first as `jordan@acme.com` sees the invitation and accepts it,
and on its next round the owner's `pendingRound()` sees
`emailHash(acceptedBy) === g.emailHash` and calls `addMember`. The
stranger gets the keys.

The same weakness reaches people who already have an account:
`shareProject()` looks the address up and seals the keys at once, so an
account squatting someone's address gets the project directly.

**How to reproduce:** against `test/fake-sync.mjs` or a dev worker: as the
owner, invite `riley@example.com` (no account). Sign up as
`riley@example.com` with any password, call `GET /v1/share-invites`, then
`POST /v1/share-invites/<id>/accept`. Run the owner's `syncShares()`. Riley's
account is now a member with keys.

**Suggested fix:** (a) make the link's token required to join: drop
`/accept` for pending invitations (or require `token` there as in
`/redeem`), and have the owner's computer add the person only for an
invitation that was redeemed with the token. (b) Verify addresses before
the service treats an account's email as identity: an emailed code at
sign-up, and only the provider's verified email from OAuth (don't fall
back to an unverified Microsoft email; use the `…@users.switchboard`
placeholder). Until (b) lands, the Team page should show the address each
person joined with and a "Check this is them" note on first join.

## H3. Shared changes find rows by uid across all your projects: they can overwrite another project's page and pull a to-do (or a bill) into the share

> **Fixed** (follow-up). Before it touches a row it already has, `mergeRows`
> (and the old-format `mergeLegacy`) checks that the row is in this share
> here. A page counts if it is in the project or added to it from another
> one (`pageLinked`, the `belongs` row). An item counts only if it is in the
> project and is a note, to-do or reminder. Anything else with that uid is
> left alone: a row moved out, a bill, or another project's page. An update
> keeps the item's own project. The web board's store has the same checks.
> Test: "a shared edit never reaches a row that is not in the project…" in
> `test/share.test.js`.

**Where:** `lib/share.js:303-306` (pages), `lib/share.js:309-311` (items),
the same in `mergeLegacy` `lib/share.js:398-406`.

**What goes wrong:** when a believed row arrives, the existing local row is
looked up with `WHERE uid = ?`, not limited to this share's project or to
uids this share has tracked. Then:
- **Pages:** `UPDATE pages SET title, body … WHERE uid = ?` overwrites the
  page wherever it is now. Today's f165ce0 means this on purpose for a
  page added from another project. But it also hits a page that was in
  the share and has since been moved to Personal or made Only me.
  `rowsSection` sends a "gone" for it, but a later edit from any member
  (for example from a laptop that was offline, with a newer `updated_at`
  than the gone mark) passes the `t.gone_at >= r.updated_at` check and
  overwrites the private copy.
- **Items:** `UPDATE items SET kind = ?, text = ?, space = ? … WHERE id = ?`
  also sets `space` to the shared project and `kind` to note/todo/reminder.
  A to-do you moved out of the shared project to Personal comes back into
  it, and on the next round `rowsSection` shares it again, with whatever
  you wrote after moving it. For an item whose uid a member knows (any item
  that was once in the share), an edit-level member can also turn one of
  your bills or invoices into a to-do in the shared project, and it is
  then sent to everyone. Today's code filters only the incoming `kind`,
  not the local one.

**How to reproduce:** share a project with a to-do in it. On your
computer, move the to-do to Personal and type a private line into it. On
the member's computer, which had it before the move and is offline, edit
the to-do, then bring it online. On your computer the to-do is back in the
shared project, with the member's text, and goes out again.

**Suggested fix:** in `mergeRows` (and `mergeLegacy`), only touch a local
row if it is in this share's project, or is a page this share's `belongs`
row points at, or its `share_rows` entry for this share has no `gone_at`.
Never change `space` or `kind` on update. Skip any local item whose kind
is not note/todo/reminder. Treat a row that arrives after this computer
sent "gone" as a new copy in the shared project, or drop it; never write
it into the row that moved away.

## M1. Each writer's own clock decides every conflict, so one wrong clock can freeze or wipe shared pages

> **Fixed** (second follow-up). Anything dated more than 10 minutes ahead
> of this computer's clock is held back and counted as refused: a row, a
> gone mark, an About card, a repo or activity list, or a policy. It goes
> through once it is no longer in the future here. Team shows
> "Jordan's computer clock is about 2 days ahead…", with what to do.
> Not done: a per-row counter (Lamport clock) in place of wall time. That
> would change what is signed, so every Switchboard would have to update at
> once. The bound above takes away the harm without that. Test: "a computer
> whose clock is far ahead cannot freeze or wipe shared pages" in
> `test/share.test.js`.

**Where:** `lib/share.js:288-307` (`updated_at` and gone `at` are taken as
sent), `lib/share.js:217` and `223` (policy `at`), `lib/share.js:339`
(About).

**What goes wrong:** `updated_at`, `d.at` and `a.at` come from the
writer's clock and are signed, but never bounded. A member whose clock
is a year ahead (or a member who wants to) writes a page with
`updated_at` in 2027. Every other computer takes it. From then on every
real edit (`updated_at = now`) loses (`cur.updated_at < r.updated_at` is
false everywhere else), and on the writer's own computer the next merge
overwrites the user's newer local edit. A gone mark dated in the future
deletes a page edited after it (`cur.updated_at > d.at` fails), and its
`share_rows.gone_at` then blocks the page from ever coming back.

**How to reproduce:** in a test, sign a row with
`updated_at: Date.now() + 365 * 86400e3` as an edit-level member and
merge. Then edit the page locally and sync: the local edit is replaced.

**Suggested fix:** refuse (count in `refused`) rows, gone marks, About
cards and policies dated more than a few minutes past this computer's
clock. For ordering, use a per-row counter (or a Lamport clock: max(seen,
own) + 1) instead of wall time.

**Where:** `lib/share.js:336-345` (mergeAbout writes the remote card into
your `profiles` setting), `lib/spaces.js:33-66` (About people become
sorting rules, by email and by full name), `lib/capture.js:89` (a
quick note typed in "All" goes to `spaceFor(text)`), `lib/terminals.js:184,
224, 314` (sessions), `server.js:329` (repos).

**What goes wrong:** 6914d9e makes the people on a project's About card
sort things into that project. 2482972 lets a shared project's owner, its
admins, or any member with About on Edit write that card on your
computer. Mail stays local, but `rowsSection` shares every note, to-do

**How to reproduce:** share a project and have the other side add

texts into a shared project, but never captures, sessions or repos. Those
should go into a shared project only when it is the current project or
chosen by name. Or: keep a remote About card's people out of
`aboutPeople()` unless you add them to your own rules. Clean `people` and
`links` on merge (strings, lengths, `https:` links only).

## M3. Each person's public keys come from the sync service and are never checked again, so a dishonest service could read a project from the next re-key on

> **Fixed** (second follow-up), without a face-to-face step:
> - **Pinned on first sight.** Each person's two public keys are kept in
>   `peerKeys`, which follows you to your own computers sealed with your
>   account key. They are kept the first time this account sees them: from
>   the service, from a policy the owner or an admin signed (grants now
>   carry the box key too), or from a signed roster (the owner's signing
>   key, across all their projects). Every key fetch for a re-key, an
>   invite, making an admin, moving an old project over, or a live session
>   goes through `keysOf()`. It refuses keys that differ from the kept ones
>   or from the signing key the signed roster or policy names. So nothing is
>   ever locked to a swapped key.
> - **Shown.** A change is kept in `keyChanged`, and Team shows an alert
>   naming the person, with the new and old check codes. Nothing new goes to
>   them until you click "The codes match: use the new keys"
>   (`trustNewKeys`). The service never replaces a sharing key (PUT is
>   set-once), so a real change means the account was reset.
> - **Check codes** (optional). Six groups of four digits from both keys.
>   You see your own code and everyone else's in a fold at the end of Team,
>   with Mark checked. Members fill in missing keys once per person during
>   sync, so everyone has everyone's code.
>
> Left: the very first sight is still trust on first use, since the service
> could swap a key before it is ever kept. Comparing check codes once is
> what closes that. Test: "people's keys are pinned on first sight…" in
> `test/share.test.js`. It swaps Jordan's key on the service, expects the
> re-key to be refused with no lock to the swapped key, and checks both
> sides' codes.

**Where:** `lib/share.js:572` (rekey seals each member's lock to
`lookup(email).pub`), `lib/share.js:793-799` and `826` (adding someone,
making someone an admin), `lib/share.js:595` (migrate).

**What goes wrong:** the file's header says the service "can neither
promote anyone nor change what leaves a computer". But the X25519 key a
lock is sealed to, and the Ed25519 key a new admin or member is trusted
with, are whatever `/v1/share-key/lookup` returns at that moment. Nothing
ties the X25519 key to the signing key pinned in the policy, and nothing
compares it with what was used last time. A service that answers a lookup
with its own key during any re-key (someone leaves, access changes) gets
the project key and every kind key. A service that answers with its own
signing key when the owner makes someone an admin can then sign policies
as that admin.

**How to reproduce:** in `test/fake-sync.mjs`, make `/v1/share-key/lookup`
return a key pair the test holds for one member, then call `setAccess`
so that a kind's readers change (which re-keys). The test can open the new
lock.

**Suggested fix:** have each account sign its X25519 key with its Ed25519
key (`{ pub, signPub, sig }`), and pin both in the policy grant when the
person is first added (the owner sees their address at that moment). At
every re-key and promotion, use the pinned keys, and refuse (with a plain
message) if the service now returns different ones. Show a short key
fingerprint on the Team page so two people can compare.

## M4. The Teams picture route's address check can be walked out of with `..` and `\`

> **Fixed** (follow-up). `isHostedUrl` (`lib/microsoft.js`) now refuses `\`
> in the address. It also parses it and requires the parsed `href` to equal
> the input exactly, the host to be `graph.microsoft.com`, and no `.` or `..`
> segment. Any tidying (`\`, `..`, `%2e%2e`, a user@host trick) changes
> the address, so it fails. `lib/conversation.js` uses the same check, so
> the page is never handed such an address. Test: "a Teams picture address
> cannot climb out of hostedContents…" in `test/conversation.test.js`.

**Where:** `lib/microsoft.js:300-307` (`HOSTED` and `hostedBytes`);
`lib/conversation.js:61` (an even looser copy).

**What goes wrong:** the check allows any characters but `/?#` in each
segment, and `fetch` then tidies the address. `\` counts as `/` in an
https URL, and `..` segments go up a level. Checked in Node:
`https://graph.microsoft.com/v1.0/chats/x/messages/y/hostedContents/..\..\..\..\..\me\messages\ID/$value`
passes the test and fetches `https://graph.microsoft.com/v1.0/me/messages/ID/$value`
(the whole raw email) with the user's Microsoft token. The address comes
from the HTML of a Teams message (anyone who can message the user writes it),
or from any web page through an `<img>` tag, since this is a GET with no header check.
The answer is never readable by the other site or the sender (it is served
to the user's own page as a picture or a download), so this is not a leak
today. It is still a token-bearing fetch of any Graph address ending
`/$value`, and it shows the user content they did not open.

**How to reproduce:** `node -e` with the regex above and `new URL(u).href`;
or open `http://127.0.0.1:4747/api/teams/picture?u=<that address, encoded>`.

**Suggested fix:** parse with `new URL()` first, then check
`url.href === input`, `url.hostname === 'graph.microsoft.com'`, and match
`url.pathname` against segments of `[A-Za-z0-9:@._=-]+` that are not `.`
or `..`. Better: build the address from the chat id, message id and
hosted id parsed out of the message, and keep only those three in the URL.
Use the same check in `conversation.js`.

  taken on trust (trust on first use). If no valid roster is there, the

  **Fixed** (second follow-up). The page already said "could not be

## Data safety

### H4. × (take out) on a page in a shared project deletes it on everyone else's computer, the author's included

> **Fixed** (follow-up). `takeOut` now checks this computer's share records
> (`sharedBy`, from `share_rows`, so it is right even before the first sync).
> If someone else shared the page, × takes it off your card only
> (`offCard`, with Undo) and the page stays in the project for everyone,
> with the toast "…Jordan shared it, so it stays in Acme for everyone". On
> your own page, × still moves it to Personal, which unshares it, and the
> toast now says so ("…no longer shared with the 2 others"). Test: "× on a
> shared page someone else wrote leaves it in the project…" in
> `test/share.test.js`.
>
> **The other path, fixed too** (third follow-up). Moving a page someone
> else shared to another project with the notebook's project menu no longer
> moves it. `POST /api/pages/<uid>` with a new `space` goes through
> `moveOwnCopy()` (`lib/sorting.js`): you get a copy of your own in the
> project you picked, and the shared page comes off your card in the shared
> project, for you only. It stays for everyone, its author included. The
> page says "Jordan shared this page, so it stays in Acme for everyone. Your
> own copy is in Personal." and opens the copy. Your own pages move as
> before. Test: "moving a page someone else shared to another project from
> the menu leaves theirs where it is" in `test/share.test.js`, through the
> real route on Jordan's computer.

**Where:** `lib/sorting.js:230` (takeOut moves the page to Personal),
`lib/share.js:266-274` (the page leaves the share, so a signed "gone" goes
out), `lib/share.js:289-291` (each other member's copy is in the shared
project, so it is deleted and tombstoned).

**What goes wrong:** the toast says the page "is in Personal now". For
everyone else in the project it is a Delete. When the page came from
another member, this is their own page, gone from all their devices (the
tombstone travels through their account). Undo works only while the toast
shows, and only on this computer. The same happens when you change a
shared page's project in the notebook's dropdown, or make it Only me. That
looks intended there, but nothing warns about it.

**How to reproduce:** Jordan writes a page in shared project Acme. Sam opens
Acme, In this project, and clicks × on it. After the next sync the page is
gone on Jordan's computer.

**Suggested fix:** in a shared project, × asks first ("This removes it for 3
people"), or leaves the page there. Better, a "gone" from someone who did
not first share the page (`origin`) only unshares it: their copy goes, and
the author's stays.

### M5. Undo (putBack) trusts the `restore` object the page sends back

> **Fixed** (second follow-up). `takeOut` keeps the Undo record on the
> server, in memory for 15 minutes, and hands the page only an id.
> `putBack` uses the kept record once, for the same project, and ignores
> whatever else the page sends. A page goes back only if it is still in
> Personal, where × put it, so a later move stands. People come back only
> if they are not on the card already, and the card is capped at 50. A
> stale or made-up Undo gets "That can no longer be undone…". Test: "Undo
> puts back only what was just taken out, as it was, once" in
> `test/sorting.test.js`.

**Where:** `lib/sorting.js:249-257`.

**What goes wrong:** `restore.page` moves *any* existing page uid into
`space`. Nothing checks that it is the page just taken out, or that it is
still in Personal, so a late or stale Undo can pull a never-shared page
into a shared project, and it is then shared. `restore.people` appends
raw objects to the About card without cleaning them, with no
de-duplication and a quiet cut at 20 (an Undo after a sync, or done twice,
duplicates people).

**Suggested fix:** keep the restore record on the server, handing the page a
short-lived id. Check that the page is still in `personal` before moving
it. Clean people and de-duplicate them by email or name.

### M6. Undo after taking out a person filed by a rule brings back the card entry, not the rule

× on Sam's row, then Undo: the rule is gone from Settings. **Fix:** put
